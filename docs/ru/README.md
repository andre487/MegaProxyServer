# Руководство MegaProxyServer

[English version](../en/README.md) · [Обзор проекта](../../README.md)

## Назначение

MegaProxyServer разворачивает HTTPS- и SSH-прокси на нескольких серверах Debian/Ubuntu. Python CLI
проверяет единый inventory и создаёт переменные Ansible, клиентские конфигурации и компактный summary
реквизитов. Ansible устанавливает и поддерживает серверные компоненты.

HTTPS обслуживает GOST в контейнере закреплённой версии. HAProxy маршрутизирует TLS по SNI, когда
один входной сервер публикует несколько chain-доменов. Системные пользователи SSH-прокси ограничены
локальным TCP forwarding: им недоступны shell, TTY, subsystem, remote forwarding и tunnel device.

## Требования

Управляющей машине нужны macOS или Linux, Git, `uv`, OpenSSH и Python 3.12+. Управляемым машинам —
актуальный Debian или Ubuntu и SSH-пользователь с `sudo`. Откройте TCP 443 для HTTPS и TCP 80 на
время standalone-проверки ACME как в firewall провайдера, так и на самом сервере.

ACME-сертификаты на публичный IP требуют Certbot 5.4+ и short-lived profile Let's Encrypt.

## Первое развёртывание

### Установка на самом сервере

Подключитесь к Debian/Ubuntu по SSH с терминалом (`ssh -t`) либо откройте консоль сервера.
Нужны root или `sudo`, установленный `curl` и доступ в интернет. Если `curl` отсутствует:

```shell
sudo apt-get update && sudo apt-get install -y curl ca-certificates
```

Запустите мастер (для root уберите `sudo`):

```shell
curl -fsSL https://raw.githubusercontent.com/andre487/MegaProxyServer/main/install.sh | sudo bash
```

Если хотите сначала прочитать скрипт, скачайте его через `curl -fsSL URL -o install.sh`,
просмотрите и выполните `sudo bash install.sh`, подставив URL из команды выше.

1. Подтвердите установку зависимостей. Репозиторий сохраняется в `/opt/megaproxy-server`;
   Python и зависимости проекта устанавливаются автоматически.
2. Укажите имя сервера, его **публичный** IP или DNS, административный логин и текущий SSH-порт.
   Выберите или создайте административный ключ, затем HTTPS и/или SSH, сертификат и пользователей.
   Для доменного ACME заранее направьте DNS на этот сервер. Откройте нужные порты у провайдера.
3. Задайте пароль Ansible Vault и сохраните его: он понадобится для следующих запусков.
4. Мастер покажет путь к административному приватному ключу. Скопируйте его на свой компьютер
   через ещё открытый административный доступ. Для root-доступа можно использовать во втором
   локальном терминале `scp root@SERVER:/ПУТЬ/К/КЛЮЧУ ./megaproxy-admin`, затем
   `chmod 600 ./megaproxy-admin`. При входе через sudo-пользователя используйте защищённую передачу
   с чтением файла через `sudo`; не делайте ключ общедоступным на сервере.
5. Только после сохранения ключа подтвердите применение. Мастер создаёт администратора локально,
   проверяет независимый SSH-вход и sudo через loopback, отключает root/парольный административный
   вход, настраивает сервисы и firewall, проверяет их и создаёт клиентские конфигурации.
6. Не закрывая исходную сессию, проверьте вход **со своего компьютера**:
   `ssh -i ./megaproxy-admin -p PORT ADMIN@SERVER`. Заберите клиентский файл
   `/opt/megaproxy-server/.generated/configs/MegaProxy.json` через защищённый канал с sudo.

Если остановились перед применением или установка завершилась ошибкой, повторите команду
установщика либо запустите:

```shell
sudo /opt/megaproxy-server/mega-proxy setup-local
```

Существующий inventory используется повторно; установщик не обновляет checkout автоматически.
Для дальнейшей работы выполняйте `sudo /opt/megaproxy-server/mega-proxy` с нужной командой.
Inventory, ключи и экспорты остаются на сервере; сохраняйте их резервные копии приватно.
В этом режиме `local: true` направляет управляющий SSH на loopback, а публичный адрес используется
в клиентских конфигурациях. Такой inventory предназначен для запуска только на этом сервере;
при переносе управления на другую машину уберите `local: true` и исправьте пути к ключам.
Мастер локальной установки настраивает один сервер; управление несколькими хостами описано ниже.

### Управление с другой машины

```shell
git clone https://github.com/andre487/MegaProxyServer.git
cd MegaProxyServer
./mega-proxy inventory
./mega-proxy bootstrap
./mega-proxy plan
./mega-proxy apply
./mega-proxy verify
```

Мастер создаёт административные ключи, реквизиты прокси и зашифрованный inventory. Путь к inventory
вне репозитория сохраняется в игнорируемом `inventory-path`. Параметр `--inventory PATH` всегда имеет
приоритет.

Для первого подключения мастер предлагает пароль или отдельный SSH-ключ. Пароль запрашивается
скрыто при bootstrap и не сохраняется в постоянном inventory; временный файл подключения удаляется
после запуска Ansible. До запуска проверьте fingerprint сервера и добавьте его ключ в `known_hosts`.
Для административного ключа с парольной фразой предварительно используйте `ssh-add`.
Получение и проверка публичного ключа также используют `ssh-keygen -y`, который может
отдельно запросить парольную фразу. Для unattended apply этот шаг должен работать без запроса.

`bootstrap` создаёт администратора с ключом и sudo, проверяет независимое подключение и `sudo -n`,
затем отключает root и парольный административный вход. После перечитывания SSH-конфигурации
доступ проверяется повторно, а inventory сразу переключается на администратора. Парольный вход
для пользователей SSH-прокси сохраняется. При ошибке повторите bootstrap: если администратор уже
доступен, первоначальный пароль больше не потребуется. Не закрывайте исходную SSH-сессию до
успешной проверки. `apply` автоматически выполняет bootstrap для выбранных новых хостов, даже
при указании тегов; для планирования нового хоста сначала выполните bootstrap отдельно.

Чтобы добавить сервер в существующий inventory:

```shell
./mega-proxy add-host
./mega-proxy bootstrap --limit proxy_new
./mega-proxy plan --limit proxy_new
./mega-proxy apply --limit proxy_new
```

Для bootstrap `--limit` принимает точные имена хостов через запятую; флаг можно повторять.
Проверка нового входа учитывает локальную SSH-конфигурацию и выводит причину ошибки SSH или sudo. Существующие настройки и
пользователи прокси сохраняются. Завершение bootstrap фиксируется отдельно для каждого хоста,
поэтому ошибка последующей установки прокси не возвращает подключение к root.

## Команды и inventory

Команды и параметры доступны в `./mega-proxy --help` и `./mega-proxy COMMAND --help`.
Глобальный параметр inventory передавайте **до** команды:

```shell
./mega-proxy --inventory /secure/inventory.yml validate
./mega-proxy --inventory /secure/inventory.yml apply --limit proxy_eu --tags https
```

Порядок поиска inventory: явный путь, затем `inventory-path`, затем `inventory.yml`. Launcher
работает из корня репозитория, относительно него разрешаются и относительные пути. `--no-hooks`
можно передавать до или после команды.

Начните с [inventory.example.yml](../../inventory.example.yml), замените примерные адреса и ключи,
затем проверьте inventory перед применением. Для серверной HTTPS-цепочки используйте полный пример
с двумя хостами [inventory.chains.example.yml](../../inventory.chains.example.yml). Допустимые поля,
правила проверки и значения по умолчанию заданы в [models.py](../../src/megaproxy_server/models.py).
Там же закреплены версии контейнеров; их можно переопределить в inventory.

Пользователи прокси задаются в глобальном разделе `users` и действуют на всех хостах с включённым
сервисом. SSH-логины прокси должны отличаться от административного. Экспорт ключа читает файл
`generated_private_key` на управляющей машине и встраивает его содержимое; одного публичного ключа
для генерации клиентского конфига недостаточно. Android MegaProxy требует приватный ключ без
парольной защиты.

Для явной привязки SSH-аккаунтов укажите у HTTPS-пользователя `ssh_users: [tun-alice]`
или выполните `./mega-proxy link-users` и выберите аккаунты из списка. Настройщик предлагает
этот выбор при создании пользователей обоих типов. Пустой или отсутствующий `ssh_users`
означает отсутствие привязки; имена автоматически не сопоставляются. Несуществующие аккаунты
и повторы отклоняются при проверке inventory. Один SSH-аккаунт можно привязать к нескольким
HTTPS-пользователям; удаление SSH-аккаунта также удаляет его привязки. Эти связи задают данные
для персональной выдачи; текущие команды `export` и `configs` по-прежнему экспортируют всех пользователей.

### SSH-сервис и выбор прямых профилей

`services.ssh.enabled` по умолчанию true: включает настройку и проверку SSH-прокси.
`services.ssh.generate_profile` по умолчанию false: выбирает хосты для прямых SSH-профилей
в `export`, `configs` и API. Административный SSH отдельно задаётся через `admin`.

Мастер отдельно спрашивает, публиковать ли прямые SSH-профили, предлагая «да»;
при отсутствии поля в ручном YAML действует false. `enabled: false`
отключает уже настроенный прокси: для HTTPS останавливает GOST, HAProxy и таймер
renewal; для SSH запрещает вход группе `megaproxy` и закрывает её сессии, сохраняя
административный SSH. Удалять службу из YAML вместо `enabled: false` не следует:
отсутствующая служба не управляется. Firewall запоминает управляемые правила и
удаляет устаревшие при следующем полном apply; остальные правила сохраняются.
Первый apply после обновления запоминает существующие настроенные порты перед
последующими изменениями; ранее открытые порты, уже отсутствующие в inventory,
автоматически не обнаруживаются.

SSH-аккаунты могут изменяться и удаляться только если их основная группа —
`megaproxy`; новые аккаунты создаются в этой группе. `removed_ssh` не допускает
администратора, bootstrap-логин, системные имена и пути. Административный
`authorized_keys` целиком управляется инвентарём: смена `admin.public_key` отзывает
старый ключ. При смене `admin.user` bootstrap сначала проверяет нового
администратора, затем удаляет прежний управляемый аккаунт и sudo-доступ, сохраняя
его файлы. Для миграции укажите `bootstrap_user` с действующим доступом.
Для ротации ключа задайте новую пару `public_key`/`private_key_file`, текущего
администратора в `bootstrap_user`, а прежний приватный ключ — в
`bootstrap_private_key_file`. Bootstrap проверяет новый вход перед отзывом старого
ключа; несовпадающая пара публичного и приватного ключей отклоняется.

Инвентарь и экспорт записываются атомарно с правами `0600`. Экспорт проверяется
до замены прежнего файла; код страны, не соответствующий двум латинским буквам в верхнем
регистре, становится пустой строкой. Справочник стран не проверяется.
Конфликты портов и HTTPS без маршрутов отклоняются до подключения к хосту.
Docker cleanup удаляет только старые образы GOST/Certbot, без глобального prune.
HTTPS-цепочки проверяют сертификат и имя выхода. CI использует локальную CA и
проверяет knock, override цепочки, TLS Jump, отказ при неправильных credentials,
сертификате или недоступном выходе; внешние домены и ACME для этих тестов не нужны.

| enabled | generate_profile | Результат |
| --- | --- | --- |
| true | true | Настройка SSH-прокси и генерация прямых SSH-профилей |
| true | false | Настройка SSH-прокси; использование хоста только в явных jump-парах |
| false | любое | Вход прокси-аккаунтам запрещается, сессии закрываются, профили не генерируются; jump-пары не допускаются |

Отключение SSH сохраняет прокси-аккаунты, но запрещает им доступ; SSH-демон сервера
продолжает работать. Для удаления аккаунта используйте `remove-users` и `apply`.
При применении с тегами включите `firewall`, чтобы обновить порты, например
`apply --tags ssh,https,firewall`.

```yaml
hosts:
  de_proxy:
    # address и admin как в inventory.example.yml
    services:
      ssh:
        title: DE
        enabled: true
        generate_profile: true
```

Названия прямых SSH-профилей берутся из обязательного `services.ssh.title`.
API не добавляет логин; файловый экспорт добавляет ` / логин`, как для HTTPS.

### Явные клиентские jump-пары

```yaml
settings:
  ssh_jump_pairs:
    - entry: de_proxy
      exit: us_proxy
      title: SSH DE -> US
      country_code: US
  https_jump_pairs:
    - entry: de_proxy
      exit: us_proxy
      title: HTTPS DE -> US
      country_code: US
```

`entry` — входной узел, `exit` — конечный прокси. SSH Jump использует один аккаунт из
`users.ssh` на обоих узлах. `export` и `configs` создают профиль для каждого SSH-аккаунта,
API — только для привязанных через `ssh_users` аккаунтов HTTPS-пользователя. Логины узлов
в паре не задаются. Оба SSH-сервиса должны быть включены; `generate_profile` может быть false.
HTTPS Jump использует HTTPS-реквизиты пользователя на обоих узлах и требует два включённых
прямых HTTPS endpoint-а. `https_chains_enabled` и chain-домен ему не нужны.

В обоих списках `title` обязателен, `country_code` необязателен.
Страна берётся у выхода. Явный код страны — две заглавные буквы.
Пустые списки не создают jump-профилей; комбинации автоматически не перебираются.
Несуществующие хосты, выключенные сервисы, повторные пары и совпадение entry/exit
отклоняются. `./mega-proxy jumps` показывает заданные SSH-пары для каждого аккаунта.
Старый флаг экспорта `--all-jumps` принимается, но не включает необъявленные пары.

Полный пример — [inventory.jumps.example.yml](../../inventory.jumps.example.yml).
`https_chain_pairs` — отдельная настройка серверных SNI-маршрутов с собственными hostname;
они экспортируются как обычные HTTPS-профили. См. [inventory.chains.example.yml](../../inventory.chains.example.yml).

### Порядок профилей

В API и MegaProxy JSON сначала идут прямые HTTPS, затем прямые SSH,
`https_chain_pairs`, `https_jump_pairs`, `ssh_jump_pairs`. Порядок прямых профилей
задаётся порядком хостов в inventory; порядок пар — порядком соответствующих списков.
MASQUE и SOCKS5 относятся к первой группе. Перестановка не меняет ID.
В HTTPS-форматах FoxyProxy, SuperProxy и ProxyList сначала идут прямые маршруты, затем цепочки.

### Названия профилей и страны

Для HTTPS- и SSH-сервисов и всех chain/jump-пар обязателен непустой `title`.
Названия берутся непосредственно из inventory; из имён хостов они не вычисляются.

Код страны прямого HTTPS берётся из первого сегмента имени хоста после удаления
необязательного префикса `proxy_`: `de_entry` и `proxy_de` дают `DE`, а `px-de` — пустой
код. Допускаются две латинские буквы в верхнем регистре; справочник стран не проверяется.
В серверных HTTPS-парах `country_code` обязателен; jump-пары могут переопределять код,
полученный из имени выхода. У прямых SSH- и SOCKS5-профилей код страны сейчас пустой.
Это подпись для отображения; фактическую страну выхода проверяйте тестом соединения в приложении.
ID HTTPS- и jump-профилей формируются из логических хостов, маршрутов и аккаунта:
изменение title или endpoint сохраняет ID. ID прямых SSH также зависят от хоста и аккаунта; в общем экспорте только ID SOCKS5
по-прежнему зависят от имени профиля.

`https_chain_pairs` создаёт только объявленные маршруты entry/exit; пустой список
не создаёт серверных цепочек. Каждому exit нужны отдельные машинные реквизиты
`chain_password`, которые не попадают в клиентский экспорт. Название цепочки берётся из обязательного `title` пары.

Knock host задаётся для каждого HTTPS-прокси через `services.https.probe_resistance.knock`:
```yaml
probe_resistance:
  enabled: true
  mode: local_decoy
  knock: [knock.example.com]
```
При включённом маскировании первый хост попадает в `browser.knockHost` в API и файловом экспорте MegaProxy.
Серверные цепочки наследуют настройку входного узла, если пара не переопределяет `probe_resistance`.
Мастер запрашивает knock host при включении маскирования.
После изменения примените HTTPS-настройки на прокси и обновите bundle конфигурационного API.
MASQUE-профили не используют knock host.

Probe resistance подавляет обычный запрос аутентификации и может нарушать работу браузерных
клиентов, ожидающих `407` перед отправкой реквизитов. Оставляйте его выключенным без проверки
нужных клиентов. Маршрут может переопределить настройку entry; `knock` разрешает обычный запрос
аутентификации для выбранных hostname-ов.

При включённом маскировании GOST отдаёт статический сайт через встроенный файловый сервер
на loopback. Python без дополнительных библиотек один раз создаёт случайный заголовок и
абстрактную SVG-картинку. Повторный `apply` сохраняет сайт; удаление
`/opt/megaproxy/decoy/index.html` приводит к новой генерации при следующем `apply`.
Страница содержит `noindex,nofollow`, а `/robots.txt` — `User-agent: *` и `Disallow: /`.
Сейчас на маскирование влияют только `enabled` и `knock`. Поля `mode`, `status_code`
и `site_title` принимаются моделью inventory, но не выбирают другой режим ответа
и не задают заголовок генерируемого сайта.

## HTTPS-сертификаты и chains

Доменные сертификаты выпускаются Certbot в standalone-режиме. Сертификат entry-сервера содержит его
direct endpoint, если он включён, и все chain-домены. После добавления пары роль находит отсутствующий
SAN, расширяет сертификат и перезапускает GOST, чтобы сертификат загрузился сразу.

До `apply` каждое chain-имя должно резолвиться в entry-сервер. HAProxy читает SNI без терминации TLS
и передаёт соединение отдельному GOST HTTP/2 listener на loopback. Затем entry подключается к
выбранному exit по машинным реквизитам. Отдельная пара в `https_chain_pairs` может переопределить
`probe_resistance` только для своего chain-маршрута.

Обновление сертификатов запускается systemd timer. Self-signed — явный запасной режим, в котором
клиент должен разрешить недоверенный сертификат прокси.

## Клиентские конфигурации

```shell
./mega-proxy configs
./mega-proxy configs --output-dir /secure/path
```

По умолчанию `.generated/configs` содержит:

- `MegaProxy.json`: HTTPS, включённые MASQUE/SOCKS5, прямые SSH хостов с `services.ssh.generate_profile: true` и явно заданные SSH/HTTPS jump-профили;
- `FoxyProxy.json`: HTTPS-профили;
- `SuperProxy.txt`: HTTPS URL с заголовком Super Proxy v1;
- `ProxyList.txt`: URL-кодированные HTTPS-прокси.

Каталог получает права `0700`, файлы — `0600`. Генерация идемпотентна и не подключается к серверам.
Экспорты содержат открытые пароли и приватные ключи — обращайтесь с ними как с секретами.

## Android MegaProxy

Персональную выдачу конфигов по HTTPS на отдельных равноправных машинах можно включить
через `services.config_api`. См. [настройку API](config-api.md) и
[пример inventory](../../inventory.config-api.example.yml).

[Экспортёр](../../src/megaproxy_server/export.py) записывает схему `net.megaproxy487.config`
v7 для базовых HTTPS/SSH-профилей и v8 при настройке `https_jump_pairs`, HTTP/3 или SOCKS5.
MASQUE-профили требуют HTTP/3. API всегда возвращает канонический v8 и фильтрует профили
для указанного клиента; браузерные проекции не включают SSH, jump и MASQUE.

### Импорт и подключение

1. Установите MegaProxy по клиентской [инструкции](https://github.com/andre487/AndroidMegaProxy/blob/main/docs/ru/installation.md).
2. Выполните `./mega-proxy configs` и приватно передайте `MegaProxy.json` на устройство. Приложение
   также импортирует созданные FoxyProxy, SuperProxy и ProxyList, но они содержат только HTTPS-маршруты.
   Для сохранения SSH-профилей, ID и настроек сертификатов используйте MegaProxy JSON.
3. Импортируйте файл и выберите нужный профиль. Проверьте маршрутизацию, DNS и failover.
4. Запустите тест соединения из меню главного экрана. Для SSH сверьте показанный fingerprint ключа
   хоста с полученным через консоль сервера или уже доверенное административное подключение.
   В SSH jump-профиле проверяются оба хоста. Публичные ключи хоста на сервере можно проверить так:

   ```shell
   for key in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf "$key" -E sha256; done
   ```

5. Подключитесь и разрешите VPN в системном диалоге Android. Тест приложения проверяет маршрут и
   фактический IP выхода; `./mega-proxy verify` проверяет развёртывание сервера и не заменяет тест
   с устройства.

Экспорт оставляет SSH fingerprint-ы доверия пустыми и сохраняет проверку ключей хостов включённой.
Для self-signed HTTPS-маршрутов MegaProxy JSON явно разрешает недоверенный сертификат прокси;
остальные форматы экспорта не передают эту настройку. Для обычной эксплуатации используйте ACME.

### Обновление импортированных профилей

После изменения серверов или реквизитов повторите `configs` и импорт JSON. Совпадающий ID обновляет
профиль, новый — добавляет. ID HTTPS-, MASQUE- и jump-профилей зависят от логических хостов,
маршрутов и аккаунтов: изменение title, страны или endpoint сохраняет ID. Переименование
хоста inventory или аккаунта меняет эти ID. ID прямых SSH зависят от логического хоста и аккаунта. ID SOCKS5 в общем экспорте зависят
от имени профиля. API использует логические идентификаторы для всех генерируемых профилей.
У дополнительных ручных профилей должны быть уникальные ID.

Приложение предлагает выборочно удалить локальные профили, отсутствующие в файле; автоматического
удаления нет. Удаление профиля на телефоне не отзывает доступ: для отзыва серверных реквизитов
используйте `remove-users` и `apply`.

Клиент сохраняет пароль и приватный ключ, если соответствующее поле JSON отсутствует; явно пустое
поле очищает значение. Наш генератор включает реквизиты, поэтому повторный импорт заменяет их.
Импорт также применяет глобальные настройки соединения, включая маршрутизацию и выключенный
failover, и заменяет настройки профилей. После импорта проверьте свои настройки устройства.
Поскольку SSH-поля доверия в экспорте пустые, может снова потребоваться подтверждение ключа хоста.

### Два способа построить HTTPS-цепочку

| Маршрут | Настройка | Что импортирует телефон |
| --- | --- | --- |
| Серверная SNI-цепочка | Задайте entry/exit и DNS по примеру chain inventory, выполните apply | Обычный `HTTPS`-профиль с chain-именем входного сервера; выход выбирает GOST |
| Клиентский HTTPS with Jump | Разверните два прямых HTTPS endpoint-а и задайте `settings.https_jump_pairs` | Профиль `HTTPS_JUMP` в JSON v8 |

Для HTTPS с Jump укажите exit в основных полях прокси, а entry — в полях Jump HTTPS proxy.
На обоих узлах используйте реквизиты глобального HTTPS-пользователя; машинный `chain_password`
предназначен для серверных цепочек. Entry должен разрешать имя exit и CONNECT к его hostname и
порту. Сертификат проверяется отдельно для каждого узла. Этот режим не требует chain-домена и
серверного `https_chains_enabled`. При отказе узла прямого переключения на exit не происходит.

Подробности — в клиентском [руководстве HTTPS with Jump](https://github.com/andre487/AndroidMegaProxy#https-with-jump).
Клиентские HTTPS jump-профили требуют приложения с поддержкой v8; старые клиенты отклоняют v8-файлы.
Серверные SNI-маршруты доступны и через форматы экспорта только для HTTPS. SSH jump-профили создаёт
`configs` и `export` из `settings.ssh_jump_pairs`. Примеры обеих настроек — в [документации API](config-api.md#явные-jump-пары).

### Ограничения клиента и диагностика

HTTPS и SSH передают TCP; MASQUE и SOCKS5 также передают UDP в совместимых сборках Android.
Доступность зависит от установленной версии клиента; см. его
[ограничения транспортов](https://github.com/andre487/AndroidMegaProxy#current-limitations).
SSH-ключи с парольной защитой не поддерживаются. DNS, маршрутизация по приложениям, failover и
Android Always-on VPN настраиваются в приложении. Экспортированные профили не включают failover.

Тест соединения помогает разделить ошибки подключения к прокси, доступа к сайту и определения IP
выхода. Он обращается к внешним тестовым сервисам через прокси; начальное разрешение имени прокси
может обращаться напрямую к внешним DoH-провайдерам до создания туннеля. Диагностические логи
остаются на устройстве, пока пользователь явно не отправит их. Адресаты запросов и правила работы
с отправленными отчётами описаны в клиентской [политике конфиденциальности](https://github.com/andre487/AndroidMegaProxy/blob/main/PRIVACY.md).
Просматривайте отчёты перед отправкой и не прикладывайте сгенерированные реквизиты к issue.

## Summary

`./mega-proxy summary` один раз выводит endpoint-ы, затем по одному разу глобальные реквизиты:

```text
Hosts:
proxy-eu.example.com (EU, HTTPS, SSH)
eu-via-us.example.com (EU -> US, HTTPS)

HTTPS:
alice
PASSWORD

SSH:
tun-alice
/path/to/private/key
```

`summary alice` выбирает точное совпадение proxy-login. Административные пользователи не выводятся.
Не сохраняйте результат в незащищённый файл или CI-лог.

## Пользователи, Vault и hooks

`remove-users` отмечает пользователей в inventory; выполните `apply`, чтобы удалить HTTPS-пользователей из GOST. Удаляемые SSH-пользователи
также попадают в глобальный tombstone-список `removed_ssh`; следующий apply удаляет их системные
аккаунты и root-owned authorized-key файлы на всех SSH-хостах. Последнего пользователя включённого
сервиса удалить нельзя.

`vault-secrets` шифрует отдельные секреты как tagged-значения Ansible Vault, оставляя хосты, порты и
флаги читаемыми. Шифрование сохраняется при дальнейших изменениях. Для unattended-запуска задайте
`ANSIBLE_VAULT_PASSWORD_FILE`, иначе CLI запросит пароль.

При каждом сохранении зашифрованного inventory CLI заново шифрует все секретные поля, включая
неизменившиеся. Ansible Vault использует случайную соль, поэтому содержимое всех `!vault`-блоков
может измениться в diff, хотя сами пароли остаются прежними. Например, bootstrap сохраняет
inventory после каждого успешно настроенного хоста при переключении на постоянного администратора.
Это текущее ограничение сохранения: исходные зашифрованные блоки для неизменившихся секретов
не сохраняются. Такие изменения сами по себе не означают смену паролей на серверах и не требуют
обновления реквизитов клиентов.

После успешного apply запускаются исполняемый `.hooks/post-config-change` и файлы из
`.hooks/post-config-change.d/` в порядке имён. Они получают `MEGAPROXY_INVENTORY`,
`MEGAPROXY_ANSIBLE_INVENTORY`, `MEGAPROXY_ROOT`, `MEGAPROXY_EVENT`. Игнорируемый каталог `.hooks`
подходит для локальных интеграций, например px-manager.

## Безопасность и эксплуатация

- Считайте inventory, `.secrets`, `.generated`, summary и экспорты секретными.
- Создавайте отдельный аккаунт или ключ для каждого человека или устройства.
- Проверяйте SSH fingerprint по доверенному каналу.
- Root SSH login отключается; постоянный администратор использует ключ и имеет sudo.
- Правила firewall облачного провайдера остаются ответственностью оператора.
- Опциональный Probe Resistance скрывает протокол от неаутентифицированных HTTP-проб, но не IP
  сервера или SNI; включайте его только после проверки нужных клиентов.

## Разработка и диагностика

`./mega-proxy check` запускает Ruff, pytest, byte-compilation и проверку синтаксиса Ansible.
CI выполняет этот набор на Python 3.12 и 3.14. Отдельные интеграционные jobs проверяют
настоящие GOST и nginx на loopback, а также Ubuntu 24.04 и два Debian 12 в LXD.
Они покрывают SSH Jump, ротацию реквизитов, удаление пользователей, отключение и повторное
включение прокси, очистку firewall и сохранение административного доступа.
Используются временные реквизиты и self-signed или локальная CA; публичный ACME, production
DNS и Android-устройство этими проверками не покрываются. Команда `check` их не запускает.

Для `main` обязательны PR, все пять проверок CI, актуальная база и закрытые обсуждения.
Force push и удаление запрещены, включая администратора; одобрение второго человека
не требуется. Имена обязательных проверок соответствуют именам jobs в workflows.

- **Ошибка ACME:** проверьте DNS, TCP 80 и firewall провайдера.
- **Chain-домен отдаёт старый сертификат:** выполните `apply --limit ENTRY --tags https`, затем
  проверьте SAN сертификата и статус `megaproxy-gost`.
- **Выбран не тот inventory:** передайте `--inventory PATH` или проверьте `inventory-path`.
- **Не обновился px-manager:** проверьте executable bit hook-а и отсутствие `--no-hooks`.
